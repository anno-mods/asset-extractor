# Asset Conversion Module Guide

@../../AGENTS.md

This guide documents specific implementation details for the asset conversion module.

## Game Knowledge Sources

### Asset Browser

The asset browser is an HTML export of all parsed game assets, generated by running `main.py`. It lets you browse every asset's properties, GUIDs, and inheritance chain.

- **Generate**: `uv run python main.py` (output goes to `config.assetbrowser_dir`)
- **Releases**: Pre-built archives are published in the `assetbrowser-YYYY-MM-DD/` directories at the project root (e.g. `assetbrowser-117/`). Open any `index.html` locally — no server needed.
- **Use**: Search by GUID, name, or template to inspect individual assets. The tree view shows the full resolved inheritance, making it the fastest way to discover attribute paths before writing extraction code.

### Anno 117 Calculator (`anno-117-calculator` repo)

The sibling repo `../anno-117-calculator/` contains two key JS data files:

| File | Contents |
|------|----------|
| `js/params-base.js` | Base-game assets only (no DLC) |
| `js/params.js` | All assets including all DLCs |

Both use the prefix `if(window.params == null)window.params=` followed by JSON. Strip the prefix to parse with `json.loads()`.

These files are the source of truth for the calculator UI and are generated by `conversion_calculator.ipynb`. They are also used by `calculator/test_unlocks.py` to verify DLC detection consistency.

### Notebook Output (`conversion_calculator.ipynb`)

The calculator notebook (`assetextractor/conversion/calculator/conversion_calculator.ipynb`) is the primary conversion pipeline. It reads parsed game assets and writes `params.js`. Key cells:

- **Cell 5**: Builds `dlc_prefix_map` (DLC ID → GUID) and `params.dlcs`
- **Cell `62e20e5a`**: Builds `dlc_unlock_map` and defines `get_unlocks(asset)`
- **Cells 16–50**: Output sections (`fertilities`, `needs`, `products`, `factories`, `buildingBuffs`, `effects`, `techs`, `items`); two cells inserted after the `effects` cell (`aa99b634`) — `mythical0items01` and `mythical0needs01` — derive `source: "mythical-item"` effect entries from every `Item.Rarity=="Mythic"`/`Item.Allocation=="Villa"` item with an island-wide (`EffectScope=="ObjectsInArea"`) `MythicEffect` referencing a `relevant_buffs` buff (no hardcoded GUID list, so new DLC items are picked up automatically), and inject matching `residenceBuildings[].needsList[]` entries (with `requiresItem` gating) for any of those buffs' `additionalNeedsDemand`

Run the notebook top-to-bottom to regenerate `params.js` after any changes to extraction logic or game data.

## Building Size Calculator

### Overview

The building size calculator (`calculator/building-sizes.py`) extracts building footprint dimensions from Anno 117 game files (.ifo files) and exports them to JSON format.

**Location**: `assetextractor/conversion/calculator/building-sizes.py`

**Output**: `building-sizes.json` - Maps building GUIDs to (width, height) tuples

### Running the Calculator

```bash
# Always run as a module from project root
uv run python -m assetextractor.conversion.calculator.building-sizes
```

**Important**: Never run as a file path (`python assetextractor/conversion/calculator/building-sizes.py`) - this will fail with `ModuleNotFoundError`.

### IFO File Resolution Strategy

The calculator uses a 5-level priority system to find IFO files for buildings:

1. **Object.Variations[0].Filename** - Standard buildings (most common)
2. **MeshGraphStyle.AdditionalConfigs[0].ConfigFile** - Gates, hedges, decorative elements
3. **Wall.TileSetCfgFolder / Aqueduct.TileSetCfgFolder** - Modular structures (returns folder path)
4. **MeshGraphEdgeSelection.HitBoxReferenceCfg** - Reference buildings
5. **Polygon.Path** - Fallback glob pattern search

**Critical**: Each priority level checks if the file/folder exists before returning. If not found, it falls through to the next priority level.

### Size Extraction Strategies

For each IFO file, the calculator tries multiple strategies in order:

1. **BuildBlocker/Position corners** - Calculates size from 4+ corner coordinates (most accurate)
2. **BoundingBox/Extents** - Uses xf/zf dimensions (less reliable, may be in physical units not grid cells)
3. **Filename pattern** - Extracts from patterns like "04x04", "1x1" in filename
4. **Asset name pattern** - Extracts from asset names like "Ornament Celtic Statue 1x1 Obelisk"

### Special Cases

#### Custom Hardcoded Sizes

Some building types don't parse well from IFO files and use hardcoded sizes:

- **MilitaryGate template**: Always returns (1, 3) regardless of IFO data

Add more custom rules in `get_custom_size_for_special_buildings()` method.

#### Modular Infrastructure

Buildings like walls, aqueducts, and fields don't have traditional sizes. These are detected and silently default to (1, 1) without logging errors:

- Templates: `Wall`, `Aqueduct`, `Field`, `MilitaryWall`
- Keywords in name: "wall", "aqueduct", "field"

#### Exclusion Filters

Assets are excluded if they match any of these criteria (case-insensitive):

- Keywords: "test", "dummy", "preview", "placeholder", "todelete", "press_version", "debug"
- Template: `MeshGraphHealthDummy`

### Error Handling

The calculator categorizes errors into three types:

1. **IFO_NOT_FOUND** - No IFO path could be resolved from asset
2. **IFO_PARSE_ERROR** - IFO file exists but failed to parse (malformed XML, missing data)
3. **NO_SIZE_DATA** - Folder exists but contains no valid IFO files

**Error Reduction**: The implementation reduced errors from 77 to 13 (83% reduction) through:
- Multi-level IFO path resolution
- Multiple size extraction fallbacks
- Asset name pattern extraction
- Modular infrastructure detection

### Common Pitfalls

1. **Gate IFO Files**: Gates often have multiple IFO files (e.g., `gate_wood_01.ifo` and `gate_wood_doors_01.ifo`). The main file may only have BoundingBox data, while the doors file has BuildBlocker data. Solution: Use custom hardcoded size for `MilitaryGate` template.

2. **BoundingBox Dimensions**: BoundingBox/Extents values are in physical units (meters), not grid cells. Small values (< 0.5) round to 0, creating invalid sizes like (0, 0), (0, 1), or (1, 0). **Fixed**: The code now detects when either dimension is 0 after rounding BoundingBox values and falls through to filename pattern extraction and asset name extraction. Walls and fields are treated as modular infrastructure and default to 1x1. Ornaments with "1x1" in their name extract size from the name pattern.

3. **File Existence**: `Object.Variations` may point to non-existent files. Solution: Verify file exists before returning path, allow fallthrough to next priority.

4. **Modular Buildings**: Walls/aqueducts reference folders via `TileSetCfgFolder`. Solution: Handle both file and folder paths in `process_assets()`.

### Testing

**Integration test**: `tests/integration/verify_building_sizes.py::test_building_size_parsing_errors`

The test runs the converter and validates:
- Total error count is acceptable (< 15)
- Errors are categorized correctly
- Report is saved to `results/test_reports/building_size_parsing_errors.txt`

**CSV validation test**: `tests/integration/verify_building_sizes.py::test_csv_loading`

Validates building sizes against expected values from CSV reference file.

## DLC Unlock Tracking (`conversion_calculator.ipynb`)

### Overview

Every output section of the calculator (`needs`, `products`, `effects`, `buffs`, `techs`, `items`, `fertilities`, `factories`) has a `"dlcUnlocks": [dlc_guid, ...]` field populated by `get_unlocks(asset)`. Multiple DLC GUIDs are unioned across all strategies, supporting future DLCs that may share assets.

**Cell structure:** Cell 5 builds `dlc_prefix_map` and `params.dlcs`. Cell 6 builds `dlc_unlock_map` and defines `get_unlocks()`.

### Detection Strategies (Cell `62e20e5a`)

| Strategy | Mechanism | Example |
|----------|-----------|---------|
| 1 | `Standard.IconFilename` contains `/dlcXX/` | needs, items, effects with DLC icons |
| 1b | `Building.AssociatedRegions` is a single DLC-exclusive region (e.g. `["Egyptian"]`) | Egyptian session buildings |
| 1c (Products) | `Product.ProductionRegions[i].RegionType` — no Roman/Celtic entry | Egyptian goods (dates, linen, papyrus) |
| 1c (Fertilities) | `Standard.Name` contains DLC-exclusive region keyword, no Roman/Celtic | Egyptian fertilities (sesame, blue lotus) |
| 1d (Items) | `Standard.Name` starts with DLC prefix (e.g. `"DLC03 ..."`) | placeholder/specialist items without DLC icons |
| 2 | `UplayProduct.UplayProductUnlocks` list | cosmetic DLC items |
| 3 | FeatureUnlock BFS seeded from `ConditionIsDLCActive` | FeatureUnlock 149405 → TechCategory 145066 |
| 3b | Trigger seed: `ConditionIsDLCActive` → `ActionRegisterTrigger` sub-trigger → `ActionUnlockAsset` | Hippodrome 152714 unlocked via DLC02 Trigger |
| 4 | BFS: TechCategory → Tech propagation | Gate techs (base icon) |
| 5 | BFS: `Tech.Rewards.Unlocks` → TechFeatureUnlock, extend BFS chain | TechFeatureUnlocks like 145339 |
| 5b | BFS: `Tech.Rewards.Unlocks` → **AssetPool**, flatten contents | buildings 145229/145230 via AssetPools 145234/145235 |
| 6 | Patron.Wonder / Patron.Shrine AssetPool flattening | Vulcan patron → AssetPool → coal mines 144810/144811 |
| 7 | Patron.LocalEffects / Patron.DominantEffects propagation | Egyptian patron effects |
| 8 | S8 propagation loop (guarded): Tech→Effects, Effect→Buffs, Item inline Buffs, BuildingBuff→AdditionalFunctionalEffect, BuildingBuff→ProvidedNeedUpgrade, Monument/Hippodrome→BuildingRank effects, Building→FunctionalEffects | Cascading DLC from tagged parents |
| 9 | Need→NeedProduct: inherits DLC from its NeedProduct | Egyptian needs (dates need, blue lotus need) |

**Guard rules in S8** (prevent false positives):
- **Effect→Buffs**: only tag buff if ALL `Effect` assets referencing it via `Effect.Buffs` are already DLC-tagged. Prevents shared buffs used by both DLC and base-game effects.
- **Item inline Buffs**: only tag buff if it has NO standalone `Effect` parents (`buff_to_effects` empty) or ALL such parents are DLC-tagged.
- **Building→FunctionalEffects**: only tag effect if ALL buildings referencing it are DLC-tagged.
- **ProvidedNeedUpgrade**: only propagate if the need's `Need.NeedProduct` is already DLC-tagged.

**Excluded from S1**: `/hall_of_fame/` icon subfolder — collector's items shipped with the base game that happen to use DLC01 icon assets (e.g. GUID 149292).

**Removed: Object.Variations filename check** — DLC01 adds volcanic visual skins to many base-game mountain buildings (limestone, iron, marble, gold mines; temples). Checking `Object.Variations` filenames for `/dlc01/` caused false positives on all of these base-game buildings. The only buildings that needed this (coal mines 144810/144811) are already covered by Strategy 6 (Patron.Wonder).

### Critical Pitfall: Tech.Rewards.Unlocks can yield AssetPools

`Tech.Rewards.Unlocks[i].UnlockReward` does **not** always point to a `TechFeatureUnlock`. It can point to an **AssetPool** of buildings that get unlocked when the tech is researched:

- Tech 145069 "Idols Chain" → `UnlockReward: 145234` (AssetPool "Roman Idols") → buildings [145223, 145220, 145231, **145229**]
- Tech 145105 "Boardgames Chain" → `UnlockReward: 145235` (AssetPool "Roman Boardgames") → buildings [145225, 145221, 145232, **145230**]

The helper `_flatten_asset_pool(reward_asset, dlc_guids)` handles this by iterating `AssetPool.AssetList`. Only actual `FeatureUnlock`/`TechFeatureUnlock` templates should be added to `fu_dlcs` for BFS chaining.

### Patron.Wonder / Patron.Shrine Chain

DLC patrons unlocked via tech rewards (e.g. Vulcan, GUID 144800, via Tech 145070) have Wonder and Shrine buildings that are DLC-exclusive. Both `Patron.Wonder` and `Patron.Shrine` are `ReferenceAttribute` pointing to `AssetPoolNamed` assets:

- Vulcan (144800) → `Wonder = 144815` (AssetPool "All Coal Mines") → [**144810**, **144811**]
- Vulcan (144800) → `Shrine = 144814` (AssetPool "All Vulcanus Shrines") → [144812, 144813]

Strategy 7 iterates all `Patron` template assets that are already in `dlc_unlock_map` and flattens their Wonder/Shrine pools.

### DLC Region Filtering (Cell 113 & 117)

Some DLC-specific effects and items are geographically restricted to their associated regions (e.g., **DLC01 "Prophecies of Ash"** is limited to the **Roman** region/Latium session).

**Mechanism**:
- `dlc_region_filter` mapping (e.g., `{dlc01_guid: ["Roman"]}`) defined in Cell 113.
- When an effect or item is unlocked by a DLC in the filter map, its `js["targets"]` list is filtered.
- The filtering logic checks each target's `Building.AssociatedRegions` (a `Flags` attribute) against the `allowed_regions` list of literals.
- Only targets that are associated with at least one of the allowed regions are retained.

**Pitfall**: `Building.AssociatedRegions()` returns a **list of literal strings** (e.g., `["Roman", "Moderate"]`). Do not attempt to compare them against GUIDs. Ensure the `dlc_region_filter` also uses the correct literal string values.

### Excluding above-threshold DLC content entirely (`dlc_region_filter.py`)

Distinct from the target-narrowing above: `assetextractor/conversion/calculator/dlc_region_filter.py` (unit-tested in `tests/integration/test_dlc_region_filter.py`) drops whole entries from every output array when they're gated behind a DLC above `include_dlcs_up_to`. Two signals are checked, since `dlcUnlocks` detection doesn't reliably cover a brand-new region the first time it ships (nothing yet references it via an `UplayProductUnlocks`-style link the way DLC01/02 extending the existing Roman region do):
1. `dlcUnlocks` tagging (`allowed_dlc_guids`).
2. Raw `associatedRegions`/`region` literals against a DLC→region map (`excluded_regions_for`), for content the `dlcUnlocks` detection missed.

**Pitfall (regression, now covered by the test suite):** for the region check, exclude an entry only if **all** of its regions are excluded, not if **any** are. Products/modules available in every region (e.g. Silo, Silica) list the new region alongside Roman/Celtic — using "any excluded region → drop" wrongly removed universally-available content the first time this was written.

## DLC Unlock Consistency Test (`calculator/test_unlocks.py`)

### Purpose

Compares `params-base.js` against `params.js` to verify `dlcUnlocks` fields are correct:
- Assets present in `params-base.js` must have `"dlcUnlocks": []` in `params.js`
- Assets absent from `params-base.js` (DLC-only) must have a non-empty `"dlcUnlocks"` in `params.js`

### File Locations

Both files live in the sibling `anno-117-calculator` repo:
- `../anno-117-calculator/js/params-base.js` — base game assets only
- `../anno-117-calculator/js/params.js` — all assets including DLC

Both use the JS prefix `if(window.params == null)window.params=` followed by JSON.

### Running

```bash
uv run python -m assetextractor.conversion.calculator.test_unlocks
```

Exits with code 1 on failure. Output: per-key stats table, then one line per violation with count and up to 3 example GUIDs.
